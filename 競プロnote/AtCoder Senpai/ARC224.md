# ARC224 分析レポート

ARC224 における **Xx_RYO_xX** の提出を、比較対象の上位5名 **Nachia（1位）、PCTprobability（2位）、potato167（3位）、maspy（4位）、Um_nik（5位）** の実際の提出コードと比較しました。

今回 Xx_RYO_xX が提出したのは **A, B, C, E** です。全体を見ると、Bの数式化はかなり良い一方、Aでは境界条件、Cでは問題の「ちょうど1つ」という条件の捉え方、Eでは削除後の**連続性を状態表現が壊していること**が主な差になっています。

特に重要なのは、単純に「上位勢の方が実装が速い」という差ではありません。**正しい不変条件をコードを書く前に確定する速さ**にかなり大きな差があります。

# A - Attach 00

提出:

- [WA 77432513](https://atcoder.jp/contests/arc224/submissions/77432513)
    
- [AC 77433161](https://atcoder.jp/contests/arc224/submissions/77433161)
    

最初のコードは、

```python
for i in range(100):
    n = k * i
    nn = str(n)
    if "00" in nn:
        print(n)
        break
```

でした。実際にこの提出はWAです。

## WAの原因

これはアルゴリズムの問題ではなく、ほぼ完全に **off-by-one** です。

`K=1` を考えるだけで、

```text
1, 2, ..., 99
```

には `"00"` がなく、最初の答えは

```text
100 = 1 × 100
```

です。

ところが、

```python
range(100)
```

は `0,1,...,99` なので、倍率100を調べません。

そしてこの問題では、もっと重要な観察があります。

> **どんな K でも `100*K` の末尾には必ず `"00"` がある。**

したがって答えの倍率は必ず100以下です。

つまり、必要十分なのは

```python
for i in range(1, 101):
```

です。

## 上位勢との比較

PCTprobability も本質的には同じ全探索をしています。

```cpp
for(ll i=1;i<=100;i++){
    ll m=i*n;
    string s=to_string(m);
    ...
    if(ok){
        cout<<m<<endl;
        break;
    }
}
```

maspy も、

```cpp
FOR(N, 1, 1000) {
    ll X = K * N;
    ...
}
```

potato167 と Nachia は上限を書かず、条件を満たすまで倍数を順番に調べています。

つまり、**方針レベルでは最初から上位勢とほぼ同じです**。

問題は、

```python
range(100)
```

を書く前に、

> 「探索はどこまでで絶対に終わる？」

を証明していなかった点です。

AC版では `range(1000)` にしてCodonへ変更していますが、本質的な修正は言語変更ではなく、**100を探索範囲に含めたこと**です。

### 推奨形

```python
for _ in range(int(input())):
    k = int(input())

    for i in range(1, 101):
        x = k * i
        if "00" in str(x):
            print(x)
            break
```

### この問題から持ち帰るべきこと

このAでは「100回くらい回せばよさそう」ではなく、

```text
100K は必ず条件を満たす
↓
倍率は高々100
↓
1..100だけ全探索
```

までをセットで考えるべきでした。

**上位勢との差は探索技法ではなく、探索上限を証明してから実装するかどうかです。**

# B - Adjacent Tiles

提出:

- [AC 77434706](https://atcoder.jp/contests/arc224/submissions/77434706)
    

あなたのコードは、

```python
from math import isqrt

def A123663(n):
    return (m := n << 1) - 1 - isqrt((m << 1) - 1)
```

でした。

## 評価

**今回提出したコードの中では、これが一番良いです。**

上位勢より短く、浮動小数点誤差もなく、`O(1)` です。

ただし、コードだけを見ると、

```python
A123663
```

と

```python
2*n - 1 - isqrt(4*n - 1)
```

が問題のどの量なのか非常に分かりにくい。

上位勢のコードと対応付けると、この式の意味が綺麗に見えます。

## Nachia / potato167 の考え方

Nachia は次の `k` を二分探索しています。

```cpp
ll kk = (k / 2) * ((k+1) / 2);
if(N <= kk) ok = k;
```

最後に

```cpp
ll ans = N * 2 - ok;
```

としています。

potato167 もほぼ同じです。

```cpp
if ((m / 2) * ((m + 1) / 2) >= N) r = m;
...
cout << N * 2 - r << "\n";
```

ここで `k` は、面積 `N` を収める長方形の縦横の和の最小値と見られます。

固定した

```text
a + b = k
```

に対して `ab` を最大にするのはできるだけ正方形に近い場合なので、

```text
max(ab) = floor(k/2) * ceil(k/2)
```

です。

したがって欲しい `k` は

```text
floor(k²/4) >= N
```

となる最小値、すなわち

```text
k = ceil(2√N)
```

です。

よって答えは

```text
2N - ceil(2√N)
```

となります。

そして整数演算では、

```text
ceil(2√N) = 1 + floor(√(4N-1))
```

なので、

```text
2N - 1 - isqrt(4N-1)
```

となります。

**あなたの式は、まさに上位勢が二分探索している値を閉形式にしたものです。**

## 改善するなら実装ではなく表現

現在の

```python
def A123663(n):
    return (m := n << 1) - 1 - isqrt((m << 1) - 1)
```

より、

```python
def solve(n):
    min_semiperimeter = isqrt(4 * n - 1) + 1
    return 2 * n - min_semiperimeter
```

の方が、後から見ても考察を復元できます。

### この問題から持ち帰るべきこと

Bについては、上位勢の方針を真似する必要はありません。

むしろ、

> 二分探索で求められる整数量を閉形式まで落とせている

という点で、あなたの解法は非常に良いです。

改善点は **「数列の答えを知っている」状態ではなく、その式が何を表すかまでコードに残すこと**です。

# C - Ascending Labels

提出:

- [WA 77439979](https://atcoder.jp/contests/arc224/submissions/77439979)
    
- [AC 77442720](https://atcoder.jp/contests/arc224/submissions/77442720)
    

ここが今回最重要です。

## 最初のWA

最初はDFSの訪問順をそのままラベルにしています。

```python
aa = 0

def dfs(pos):
    nonlocal aa
    visited[pos] = aa
    aa += 1
    for nex in g[pos]:
        if visited[nex] == -1:
            dfs(nex)
```

これは、

> 各頂点に異なる番号をDFS順に付ける

という構成ですが、問題が要求しているのはそうではありません。

要求は、

> `A_v - 1` のラベルを持つ隣接頂点が**ちょうど1個**

です。

例えば木

```text
1 - 2 - 4
|
3
```

を `1 → 2 → 4 → 3` の順でDFSすると、

```text
A1=0
A2=1
A4=2
A3=3
```

となります。

しかし頂点3の唯一の隣接点1はラベル0です。

```text
A3 - 1 = 2
```

を持つ隣接点は存在せず、失敗します。

つまり必要なのは**訪問順ではなく、DFS木上の深さ**です。

---

## 上位勢の解法

Nachia はそのまま、

```cpp
auto dfs = [&](auto& dfs, ll v, ll d) -> void {
    vis[v] = 1;
    ans[v] = d;
    for(ll w : adj[v]) if(!vis[w]){
        dfs(dfs, w, d + 1);
    }
};
```

です。

potato167 も、

```cpp
A[x] = A[var] + 1;
self(self, x);
```

だけです。

さらに提出中に

```cpp
for (auto x : G[i])
    if (A[x] + 1 == A[i]) ok++;

assert(ok == 1);
```

と、問題の条件そのものを検証しています。

この `assert` はかなり参考になります。

「たぶんDFS深さでいける」ではなく、実装後に

```text
各頂点について predecessor が本当に1個か
```

を直接チェックしています。

---

## 面白い点：上位勢も一度間違えている

maspy の最初の提出は最短距離でした。

```cpp
auto [dist, par] = bfs01<int>(G, 0);
print(dist);
```

そして **WA** になっています。

PCTprobability も最初はDijkstra相当でWAし、その後DFSに変更しています。

なぜ最短距離がダメか。

BFS距離なら、ある頂点 `v` に対して

```text
distance = d-1
```

の隣接点が**複数存在する**ことがあります。

問題文は「少なくとも1つ」ではなく、

> **ちょうど1つ**

です。

maspy の修正版には実際に、

```cpp
/*
wow
「ちょうど」ひとつとのこと
*/
```

というコメントまで残っています。

そして修正版はDFS深さです。

これはかなり重要です。

**このCは、グラフアルゴリズムの知識ではなく、「ちょうど1個」という一語に反応できるかの問題だった**と見るべきです。

---

## あなたのACコード

最終的には、

```python
def dfs(pos):
    a = -1
    for nex in g[pos]:
        a = max(a, visited[nex])
    visited[pos] = a + 1

    for nex in g[pos]:
        if visited[nex] == -1:
            dfs(nex)
```

でACしています。

これは面白いコードで、実は再帰DFSの性質上、

```python
a = max(a, visited[nex])
visited[pos] = a + 1
```

はほぼ

```python
visited[pos] = visited[parent] + 1
```

を遠回りに計算しています。

新しい頂点 `v` がDFSで初めて発見された瞬間、すでに訪問済みで `v` に隣接している頂点は基本的に現在のDFSスタック上の祖先です。

その中で最も深いのが親なので、

```text
max(訪問済み隣接点のラベル) = 親のラベル
```

となります。

つまりあなたは最終的に、**DFS深さという正解を別の形から再発見しています。**

それなら上位勢と同じく、

```python
visited[nex] = visited[pos] + 1
```

で十分です。

### 簡略化版

```python
visited = [-1] * (n + 1)
visited[1] = 0

def dfs(v):
    for u in g[v]:
        if visited[u] != -1:
            continue
        visited[u] = visited[v] + 1
        dfs(u)

dfs(1)
```

この形にできるかどうかが、**考察が完全に整理できたかの目安**になります。

---

## Cでの時間差をどう見るか

最初のWAそのものは問題ではありません。

上位勢もWAしています。

違いは修正速度です。

- PCTprobability: WA → AC 約 **2分22秒**
    
- maspy: WA → AC 約 **7分39秒**
    
- Xx_RYO_xX: WA → AC **23分30秒**
    

上位勢はWAを見て、

```text
最短距離・訪問順ではダメ
↓
「ちょうど1つ」を保証したい
↓
親を一意に作ればよい
↓
DFS木の深さ
```

まで素早く縮約しています。

あなたはACには到達しましたが、最終コードにも

```python
max(visited[nex])
```

が残っており、まだ「親1個だけを意識すればよい」というところまで単純化し切れていません。

ここがCで最も伸ばせる部分です。

# E - ABC|AB|A

提出:

- [WA 77445608](https://atcoder.jp/contests/arc224/submissions/77445608)
    

あなたのコードはかなり考えた跡があります。

```python
case "A":
    stack.append(S)
    a_idx.append(len(stack) - 1)

case "B":
    if a_idx:
        pos = a_idx.pop()
        stack[pos] = "AB"
```

そしてCでは、

```python
while stack:
    last = stack.pop()
    if last == "A":
        a_idx.pop()
    else:
        break
```

としています。

## WAの本質

問題は、

> **過去のAをインデックスで直接参照してしまい、「部分文字列」という制約を壊している**

ことです。

具体的には、問題文のサンプルにある

```text
AABBCC
```

を見るだけで壊れます。

正答は `1` ですが、あなたのコードでは `0` になります。

途中状態を見ると、

```text
A
AA
```

から最初の `B` を読んだとき、

```text
[A, AB]
```

のような状態になります。

次の `B` で `a_idx` の残りを使って、

```text
[AB, AB]
```

にしてしまいます。

しかしこれは不正です。

最初にできた `"AB"` が途中に存在している以上、左側のAと右側のBは連続していません。

つまり、

```python
pos = a_idx.pop()
stack[pos] = "AB"
```

によって、**スタック上の障害物を飛び越えてマッチングしている**のが原因です。

文字列削除問題では非常に危険な状態表現です。

---

# 上位勢のE解法

Nachia のコードが非常に綺麗です。

```cpp
reverse(S.begin(), S.end());
string buf;

for(char c : S){
    if(c == 'A'){
        if(buf.size() && buf.back() == 'B'){
            buf.pop_back();
            if(buf.size() && buf.back() == 'C'){
                buf.pop_back();
            }
        }
    } else {
        buf.push_back(c);
    }
}

cout << buf.size() << "\n";
```

## なぜ逆から見るのか

削除できる文字列は全部

```text
A
AB
ABC
```

であり、**必ずAから始まります**。

前から処理すると、Aを見た時点では

```text
Aだけで消す？
ABにする？
ABCまで伸ばす？
```

がまだ決まりません。

だからあなたのコードでは `a_idx` や `"AB"` という「未確定状態」を持つ必要が生じています。

逆から処理すると、Aを見た瞬間には右側がすでに確定しています。

右側の残りが

```text
B C ...
```

なら `ABC` として消せる。

```text
B ...
```

なら `AB` として消せる。

それ以外ならA単体で消す。

つまり **未来の情報を待つ必要がありません。**

これが上位勢のコードが異常に短い理由です。

---

## Pythonにそのまま移すなら

```python
def solve(s):
    buf = []

    for c in reversed(s):
        if c == "A":
            if buf and buf[-1] == "B":
                buf.pop()

                if buf and buf[-1] == "C":
                    buf.pop()
        else:
            buf.append(c)

    return len(buf)
```

状態は、

> 「すでに処理した右側で、まだ消えていないB/C」

だけです。

`A` は必ず単独でも消せるため、スタックにAを残す必要すらありません。

これはあなたの

```python
stack = []
a_idx = []
ans = 0
```

という3状態から、

```python
buf = []
```

だけに落とせます。

---

## Eで学ぶべきパターン

この問題で重要なのは「スタック問題をもっと練習する」ではありません。

今回の上位コードから抽出すべきなのは、

> **操作の始点が全部同じ文字なら、逆向きに見ることで未確定状態を消せないか？**

です。

今回、

```text
A
AB
ABC
```

はすべてA始まりです。

そのため右から見れば、Aを処理した瞬間に選択を確定できます。

これはかなり再利用性の高い発想です。

---

# D / F を含むコンテスト全体の立ち回り

あなたはBを18:42で通した後、Cの最初の提出が53:38です。

つまりB ACからC WAまで約35分使っています。

さらにC修正に約23分30秒を使い、C ACが77:08。

そこからEに約32分使って109:09でWA、D/Fには提出していません。

一方で比較対象5人は、全員FまでACしています。

ただし、**「Eへ行った判断が悪かった」とは言えません。**

例えばmaspyは、

```text
A  01:03
B  04:11
C  05:11 WA
E  10:19 AC
C  12:50 AC
D  16:38 AC
F  36:36 AC
```

という順です。

つまり、Cで詰まった後にEへ回ること自体は、上位勢も実際にやっています。

あなたの場合の問題は問題選択より、

> **CでもEでも、状態・不変条件を複雑なまま実装へ持ち込んでいる**

ことです。

---

# 総合評価

## 1. 強みは「数式を圧縮する力」

Bが典型です。

上位勢が

```cpp
if ((m / 2) * ((m + 1) / 2) >= N)
```

を二分探索しているところを、

```python
2 * n - 1 - isqrt(4 * n - 1)
```

まで落としています。

これは明確な強みです。

今後も捨てるべきではありません。

---

## 2. 一番改善効果が高いのは「コードを書く前の不変条件の言語化」

今回4問すべてに現れています。

Aなら、

```text
100K が必ず条件を満たす
```

Cなら、

```text
各頂点には predecessor を1人だけ作りたい
→ DFSの親をそれにする
```

Eなら、

```text
Aは必ず消える
→ 右側にB, Cが残っているかだけ見ればいい
```

です。

上位勢の最終コードが短いのは、単にC++力が高いからではなく、**実装前に状態をここまで圧縮しているから**です。

---

## 3. 「WA後にコードを修正する」より「反例から仮定を1個壊す」

Aでは `K=1`。

Cでは、

```text
1 - 2 - 4
|
3
```

Eではサンプルそのものの

```text
AABBCC
```

です。

いずれも巨大ケースは不要です。

今回のWAは3問とも、**小さい例で現在の状態表現を手計算すれば発見できる種類**でした。

特にCで上位勢のWA→ACが速かった理由は、アルゴリズムを一から考え直したというより、

```text
BFS距離だと predecessor が複数になる
```

という失敗した仮定をすぐ特定したからだとコードから読み取れます。

---

# 今回の優先復習ポイント

優先順位を付けるなら次の3つです。

1. **Cをもう一度、`A[child] = A[parent] + 1` だけで書く。**  
    なぜ「ちょうど1つ」が保証されるのかを、DFSの探索途中に存在しうる辺まで含めて説明できる状態にする。
    
2. **Eを逆向き1スタックで書き直す。**  
    特に「なぜ `a_idx` 方式はAABBCCで連続性を壊すのか」を説明できるようにする。
    
3. **Aでは `100K` という上界証明を先に書く。**  
    探索回数を勘で置かず、「必ず存在する候補」から上界を作る癖をつける。
    

Bについては追加の解法練習より、現在の式を

```text
2N - 最小半周長
```

まで説明できれば十分です。

今回の比較から見る限り、必要なのはより高度なデータ構造やテンプレートではありません。**Bで見せている「本質を式1つまで圧縮する力」を、Cの構成問題やEの文字列操作にも適用すること**が、上位5名との差を最も直接的に縮めるポイントです。
