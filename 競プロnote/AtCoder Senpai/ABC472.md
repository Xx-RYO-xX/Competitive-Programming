# ABC472 分析レポート

AtCoder ABC472 について、Xx_RYO_xX の全提出と、比較対象の **maspy（1位）、shiomusubi496（2位）、Nachia（3位）、jiangchenys（4位）、krrajeev（5位）** の提出を比較しました。

結論から言うと、今回の差は「難しいアルゴリズムを知らない」というより、**標準的な形に落とし込むまでの速度と、必要以上に一般的・重い実装を選んでしまう点**にかなり集約されています。C・D・最終的なEは方針レベルでは上位勢とかなり近いです。一方でBでは素直な累積和より重い実装、Dでは `bool` で済む状態を `set` で保持、Eでは「奇閉路を1個見つける」ために「全単純閉路を列挙する」という大きすぎる問題を解いています。

---

|---|--:|--:|---|
|A|01:20|01:53|十分速い|
|B|05:28|03:36|少し差|

# 2. A - A

あなたの提出: [78585011](https://atcoder.jp/contests/abc472/submissions/78585011)

あなたのコードは次の形です。

```python
s = list(input())[:-1]

for S in s:
    if S != "A":
        print(".", end="")
    else:
        print(S, end="")
```

一方、Nachia は、

```cpp
string s; cin >> s;
for(char& c : s) if(c != 'A') c = '.';
cout << s << "\n";
```

と、**文字列そのものを書き換えて最後に一度だけ出力**しています。

### 添削

方針上は何も問題ありません。ただし、

```python
list(input())[:-1]
```

は避けたいです。

`sys.stdin.readline()` が末尾に `\n` を含むことを前提として最後の1文字を無条件で捨てています。競プロの入力ではほぼ問題になりませんが、本質的には「改行を除去する」処理なので、

```python
s = input().strip()
```

でよいです。

さらに、一文字ずつ `print(..., end="")` するより、

```python
s = input().strip()
print("".join(c if c == "A" else "." for c in s))
```

のように、**答えを構築して一度出力する**形の方が競プロでは扱いやすいです。

Aなので順位に影響するほどではありませんが、「I/Oを細切れにしない」という癖は後々効いてきます。

# 3. B - Break a Stick

あなたの提出: [78592740](https://atcoder.jp/contests/abc472/submissions/78592740)

ここは小さいですが、今回かなり重要な改善点があります。

あなたは、

```python
ans = float("inf")
for i in range(n):
    left = sum(l[0 : i + 1])
    right = sum(l[i + 1 :])
    ans = min(ans, abs(left - right))
```

としています。

Nachia は累積和を作り、

```cpp
V<ll> pos(N+1);
REP(i,N) pos[i+1] = pos[i] + A[i];

for(ll i=1; i<N; i++){
    ll a = pos[N] - pos[i];
    ll b = pos[i];
    chmin(ans, max(a,b) - min(a,b));
}
```

です。

### 問題点1: `sum` を毎回計算している

あなたのコードは各 `i` について、

```python
sum(l[:i+1])
sum(l[i+1:])
```

を計算しているため $O(N^2)$ です。

今回は $N\le100$ なので全く問題ありませんが、この問題ではもっと自然に、

```python
total = sum(l)
left = 0

for i in range(n - 1):
    left += l[i]
    right = total - left
    ans = min(ans, abs(left - right))
```

と書けます。

これは「高速化テクニック」というより、**状態を1回の走査で更新する問題として捉える**という差です。

### 問題点2: `range(n)` は実は1回多い

棒の切れ込みは `N-1` 箇所しかないので、

```python
for i in range(n):
```

の最後の `i=n-1` は、

```text
left = 棒全体
right = 0
```

という、存在しない切断を調べています。

今回はすべての長さが正なので、この候補の差は棒全体の長さになり、正しい切断より良くなることはありません。そのためACしています。

ただし、これは**制約のおかげで答えを壊さなかった off-by-one**です。

今回のBで上位勢から最も真似したいのは、アルゴリズムより、

> 「切れ込みは N-1 個」→ `for i in range(n-1)`

と、問題文の対象をコード上でもそのまま表現することです。

# 4. C - On a Diet

あなたの提出: [78606364](https://atcoder.jp/contests/abc472/submissions/78606364)

ここはかなり良いです。

あなたは、

```python
eat = 0
eated = [False] * (n + 1)

for i in range(1, n + 1):
    l = max(i - m + 1, 1) - 1
    eat -= a[l] if eated[l] else 0

    if eat + a[i] <= k:
        eat = eat + a[i]
        eated[i] = True
        print("Yes")
    else:
        print("No")
```

とし、**現在の直近M日間に実際に食べたカロリーだけを `eat` に保持**しています。計算量は $O(N)$ です。

Nachia は少し異なる表現で、

```cpp
if(A[i] + sum[i] - sum[max<ll>(0,i+1-M)] <= K){
    cout << "Yes\n";
    sum[i+1] = sum[i] + A[i];
} else {
    cout << "No\n";
    sum[i+1] = sum[i];
}
```

と、「それまでに実際に食べたカロリー」の累積和を使っています。

### 方針比較

これは優劣というより、

- あなた: sliding window
    
- Nachia: prefix sum
    
- jiangchenys: 食べたおやつだけqueueに保持
    
- krrajeev: あなたとほぼ同じ「M日前を引く」方式
    

という違いです。

**あなたの方針は上位勢と同等です。**

したがってCが20:50までかかった原因を「アルゴリズムの弱さ」と考える必要はありません。

### 実装だけ少し整理できる

この部分、

```python
l = max(i - m + 1, 1) - 1
eat -= a[l] if eated[l] else 0
```

は正しいですが、一読して「M日前をwindowから追い出している」と分かりづらいです。

例えば、

```python
old = i - m
if old >= 1 and eated[old]:
    eat -= a[old]
```

の方が意味が直接出ます。

変数名も、

```python
eat
eated
```

より、

```python
window_sum
ate
```

などの方が、考察とコードの対応が明確になります。

この問題については、**方針を変えるより、15分かかった考察・実装を5分程度で再現できるようにすること**が課題です。

# 5. D - Bomber Mad

あなたの提出: [78618645](https://atcoder.jp/contests/abc472/submissions/78618645)

この問題は、結果だけ見ると44:41ですが、**アルゴリズム自体は上位勢とほぼ完全に同じです。**

あなたはまず爆弾の存在する行・列を管理し、

```python
h_to_w = []
for _ in range(h):
    ...
    hwt = set()
    for i in range(w):
        if st[i] == "#":
            hwt.add(i)
```

列方向も、

```python
w_to_h = []
for _ in range(w):
    wht = set()
    for i in range(h):
        if s[i][_] == "#":
            wht.add(i)
```

としています。

そして、

```python
if (not h_to_w[i]) and (not w_to_h[j]):
    dist[i][j] = 0
    q.append((i, j))
```

で安全マスを全部始点にした multi-source BFS をしています。

Nachia も全く同じ本質で、

```cpp
V<ll> exrow(H), excol(W);

REP(y,H) REP(x,W) if(S[y][x] == '#'){
    exrow[y] = excol[x] = 1;
}

REP(y,H) REP(x,W)
    if(!exrow[y] && !excol[x])
        D[y][x] = 0;
```

からmulti-source BFSをしています。

### 最大の改善点: `set` が情報を持ちすぎている

あなたが後で使用している情報は、

```python
not h_to_w[i]
not w_to_h[j]
```

だけです。

つまり必要なのは、

> その行/列に爆弾が「存在するか」

だけです。

ところが実際には、

```python
set()
```

に「どの位置に爆弾があるか」まで保存しています。

上位コードのように、

```python
row_has_bomb = [False] * h
col_has_bomb = [False] * w

for i in range(h):
    for j in range(w):
        if s[i][j] == "#":
            row_has_bomb[i] = True
            col_has_bomb[j] = True
```

だけで十分です。

これは今回のコード全体で何度か見られる特徴です。

> **必要な情報より一般的なデータ構造を持ってしまう。**

Eの `simple_cycles` も、この延長線上にあります。

### BFS自体は良い

```python
dist = [[-1] * w for _ in range(h)]
...
while q:
    i, j = q.popleft()
```

というmulti-source BFSは正解そのものです。

細かいところでは、

```python
direction = {(0, -1), (0, 1), (-1, 0), (1, 0)}
```

を `set` にする必要もありません。

```python
directions = ((0, -1), (0, 1), (-1, 0), (1, 0))
```

で十分です。

また、jiangchenys は距離が `K` に達した頂点からはそれ以上BFSしないようにしており、答えだけ欲しいならこちらの方が無駄がありません。

Dでの23分超の消費は、アルゴリズムの不足というより、**問題を必要最小限の状態に整理する速度**の問題に見えます。

# 6. E - Odd Cycle

ここが今回最重要です。

提出:

- [78625863 / PyPy / TLE](https://atcoder.jp/contests/abc472/submissions/78625863)
    
- [78626058 / CPython / TLE](https://atcoder.jp/contests/abc472/submissions/78626058)
    
- [78634285 / PyPy / AC](https://atcoder.jp/contests/abc472/submissions/78634285)
    

最初の提出は、

```python
import networkx as nx

...

cycle = list(nx.simple_cycles(graph))
for c in cycle:
    if len(c) % 2 != 0:
        print(len(c))
        print(*c)
        break
```

でした。最初のPyPy版は実行時間2秒超かつメモリ1GiB超、CPythonに変えてもTLEしています。

### TLEの本質

問題が要求しているのは、

> 奇閉路が存在するか。存在するなら1個。

です。

しかし、

```python
nx.simple_cycles(graph)
```

で解いているのは、

> 単純閉路を全部列挙する。

という、はるかに大きな問題です。

さらに、

```python
list(nx.simple_cycles(graph))
```

なので、最初の奇閉路を見つける前に**列挙結果を全部メモリに載せようとしています**。

単純閉路の個数はグラフによって指数的に増え得ます。

したがって、

```text
PyPyが遅い？
↓
CPythonに変更
```

では改善しません。

この段階でまず見るべきだったのは言語ではなく、

```text
N, M の総和 <= 2×10^5

→ O(N+M) / O((N+M)logN) 程度が欲しい
→ 閉路列挙は絶対に違う
```

という計算量です。

---

## 最終ACは非常に良い

最終的には、

```python
dist = [0] * (n + 1)

q = deque([1])
dist[1] = 1
oya = [-1] * (n + 1)
```

として二部グラフ判定を行い、

```python
nex_coler = -1 * dist[pos]

if dist[nex] == 0:
    dist[nex] = nex_coler
    q.append(nex)
    oya[nex] = pos
elif dist[nex] == nex_coler * -1:
    s, t = nex, pos
```

と、同色の辺を見つけています。

これは本質的に、

```python
color[nex] = -color[pos]

# すでに同色なら奇閉路
if color[nex] == color[pos]:
```

です。

**「奇閉路がある ⇔ 二部グラフでない」**にちゃんと落とせています。

計算量も $O(N+M)$ です。

---

## 閉路復元も面白い

あなたは、

```python
while s != t:
    anss.append(s)
    anst.append(t)
    s = oya[s]
    t = oya[t]

anss.append(s)
ans = anss + anst[::-1]
```

と、両端を同時に親へ上げています。

普通なら「深さが違ったら壊れるのでは？」と思う部分です。

しかし今回、`s,t` は BFS 木における **同じ色の隣接頂点**です。

BFSでは辺 `(s,t)` に対して深さの差は高々1です。一方、同じ色なら深さの偶奇は同じです。

したがって、

```text
|depth[s] - depth[t]| <= 1
かつ
depth[s] ≡ depth[t] (mod 2)

→ depth[s] = depth[t]
```

となり、同時に上げてよいわけです。

ここはかなり良いです。

ただし、**その成立理由がコードに全く現れていない**ことが弱点です。

---

## jiangchenys のコードとの比較

jiangchenys は、

```cpp
vector<int> col(n + 1, -1), par(n + 1, 0), dep(n + 1, 0);
```

と、色だけでなく明示的に `dep` を持っています。

復元も、

```cpp
while (dep[x] > dep[y]) {
    a.push_back(x);
    x = par[x];
}
while (dep[y] > dep[x]) {
    b.push_back(y);
    y = par[y];
}
while (x != y) {
    a.push_back(x);
    b.push_back(y);
    x = par[x];
    y = par[y];
}
```

です。

こちらは少し長いですが、一般の木上の2頂点のパス復元としてそのまま使えます。

Nachia はさらに別方式で、両端から根までのパスを全部作って、

```cpp
while(A.size() && B.size() && A.back() == B.back()){
    rt = A.back();
    A.pop_back();
    B.pop_back();
}
```

と共通部分を削っています。

### Eについての評価

最終コードだけなら十分良いです。

今回の問題は、

> **ACコードを改善することより、「最初からこのACコードに行く」こと**

が課題です。

特に、

```text
奇数長閉路
↓
二部グラフ判定
↓
同色辺が奇閉路の証拠
↓
親を持てば復元できる
```

という連想を即座に出せるようにしたいです。

# 7. F - Centroid of a Slice（未提出）

あなたの提出はありません。一方、比較対象5名は全員ACしています。

jiangchenys の提出は 28:38 で、かなり短くまとまっています。

```cpp
long long cross = X[i] * Y[i + 1] - X[i + 1] * Y[i];

SA[i + 1] = SA[i] + cross;
SX[i + 1] = SX[i] + (X[i] + X[i + 1]) * cross;
SY[i + 1] = SY[i] + (Y[i] + Y[i + 1]) * cross;
```

を前計算し、各クエリについて、

```cpp
long long A = SA[R] - SA[L] + cLR;

double cx =
    (double)(SX[R] - SX[L] + (X[R] + X[L]) * cLR)
    / (3.0 * A);

double cy =
    (double)(SY[R] - SY[L] + (Y[R] + Y[L]) * cLR)
    / (3.0 * A);
```

としています。

提出: [jiangchenys 78611095](https://atcoder.jp/contests/abc472/submissions/78611095)

本質は、

1. 多角形の面積を外積の和で表す
    
2. 多角形重心も各辺の外積の重み付き和で表す
    
3. それらを累積和にする
    
4. 円環を2周分持って区間クエリにする
    

です。

つまりFで学ぶべきなのは特殊な幾何テクニックというより、

> **「加法的な量なら、円環上でも累積和クエリにできる」**

という形です。

ただし、重心公式自体を知らなければコンテスト中に導出するのはかなり重いので、これは今回の比較対象から新しく吸収すべき知識です。

# 8. G - Cascading Grid（未提出）

Gはさらに面白いです。

Nachia のコードは `atcoder::mf_graph` を用いた非常に短い最大流です。

```cpp
if(S[y][x] == '-'){
    mf.add_edge(idx(y,x), snk, 1);
}
if(S[y][x] == '+'){
    offset++;
    mf.add_edge(src, idx(y,x), 1);
}
```

そしてマス間に、

```cpp
mf.add_edge(idx(y+1,x), idx(y,x), INF);
```

縦には「下 → 上」、横には両方向の無限容量辺を張っています。

最後は、

```cpp
ll ans = offset - mf.flow(src, snk);
```

だけです。

提出: [Nachia 78617717](https://atcoder.jp/contests/abc472/submissions/78617717)

### これは最大重み閉包問題

あるマスを残すとします。

上下について、下のマスを残しているのに上のマスを消すことはできません。上から操作すると下まで巻き込まれるからです。

したがって、

```text
下を残す ⇒ 上も残す
```

という implication ができます。

横方向は相互に到達できるので、

```text
左を残す ⇔ 右も残す
```

です。

あとは、

```text
+ を残す : +1
- を残す : -1
```

という最大重み閉包になり、min-cutで解けます。

これは「燃やす埋める / Project Selection Problem」の典型です。

実際、shiomusubi496 は自身の `ProjectSelectionProblem` ライブラリをそのまま利用して解いており、Nachia はAtCoder Libraryのmaxflowに直接落としています。

ここは今後かなり価値のある引き出しです。

> 「Aを選んだらBも選ばなければならない」という制約付きの最大利益

を見たら、最大重み閉包 → min-cut を疑えるようにするとよいです。

# 9. 上位勢との実装上の差

今回のA～Eを横断すると、一番顕著なのは **データ構造の選び方**です。

あなたは、

```python
# A
list(input())[:-1]

# B
sum(l[:i+1])
sum(l[i+1:])

# D
hwt = set()
wht = set()

# E
nx.simple_cycles(graph)
```

と、必要なものより一段大きな操作・表現を選ぶ傾向があります。

一方、比較対象コードは、

```text
A: 文字列を直接置換
B: running sum / prefix sum
C: running sum / prefix sum
D: rowBomb, colBomb という bool
E: color + parent
```

と、**問題が要求する最小限の情報だけを保持する**コードになっています。

この差は実行速度より、考察速度とバグ率に効きます。

特にDは象徴的で、あなたもNachiaも最終的には同じmulti-source BFSなのに、

```text
「行に爆弾があるか」
```

という1 bitの情報に対して、あなたは `set` を作っています。

ここを縮める思考ができれば、Dの実装量もかなり減ります。

# 10. 今回から優先して直したいこと

1. **制約を見た直後に、許容計算量を書く。**  
    Eなら `ΣN,ΣM <= 2e5` を見た時点で「ほぼ線形」と決めるべきです。`simple_cycles` を思いついても、「これは全列挙では？」と提出前に止まれます。
    
2. **「何を知る必要があるか」を最小化してからデータ構造を決める。**  
    Dなら「爆弾位置集合」ではなく「爆弾が1個でも存在するか」。Bなら「左右の配列」ではなく「左和と全体和」。
    
3. **よく使う状態更新を定型化する。**  
    Cのような固定長windowなら、「入るものを足す・M日前を引く」をすぐ書けるようにする。あなたのCは方針として既に十分なので、速度だけ改善対象です。
    
4. **グラフの存在判定では、対象そのものを列挙しない。**  
    Eは今回最大の教訓です。「奇閉路を探す」を「閉路列挙」と受け取らず、「奇閉路が存在しないグラフは何か？」→「二部グラフ」と逆側から考える癖が有効です。
    
5. **次に吸収するならFとGの上位コード。**  
    Fの「shoelace公式 + first moment + 円環累積和」と、Gの「implication → maximum closure → min-cut」は、今回の比較対象が明確に持っていて、あなたの提出にはまだ現れていない引き出しです。

# 総評

A～Dを見る限り、基礎的な実装力が原因で解けていないわけではありません。特にCは上位勢と同等の $O(N)$、Dは上位勢と同じmulti-source BFS、Eも最終的には正しい $O(N+M)$ の二部グラフ判定まで自力で修正できています。

今回もっとも大きかったのは **「最初に問題をどのサイズの問題として捉えるか」** です。

Bでは本来1本のrunning sumで済むところを毎回 `sum` し、Dでは1 bitで済むところを `set` にし、Eでは存在判定で済むところを全単純閉路列挙にしています。この3問はかなり同じ傾向を示しています。

次回のコンテストでは、実装前に一度だけ、

```text
欲しい答えは何か？
そのために本当に保持する必要がある情報は何か？
制約上、何回まで全体を走査できるか？
```

を明示すると、今回のB→C→D→Eで発生した時間差をかなり縮められるはずです。

特にEは、**TLEコードから最終ACコードへの改善幅そのものが、今回鍛えるべきポイントを非常によく表しています。** `simple_cycles` から `color + parent` まで問題を縮約できたので、次はその縮約を提出1回目より前に行うことが目標です。
