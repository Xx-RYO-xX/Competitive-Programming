今回 Xx_RYO_xX が実際に提出したのは **A・C** であるため、この2問はコードレベルまで詳細に添削する。

結論から言うと、今回かなり特徴的なのは、

つまり今回の改善ポイントは、難しいアルゴリズムの知識というより、

1. **構成問題では不変量を明文化してから実装する**
    
2. **貪欲を書く前に目的関数を式変形する**

# 2. A - AtCoder Reverse Contest

あなたの提出：

- [78972844 - WA](https://atcoder.jp/contests/arc229/submissions/78972844)
    
- [78973973 - WA](https://atcoder.jp/contests/arc229/submissions/78973973)
    
- [78974261 - AC](https://atcoder.jp/contests/arc229/submissions/78974261)
    

## あなたの考察

最終ACコードの中心部分は、

```python
al = x //25
ar = x % 25
ans = "a"*al

ans += "c"*25
ans = list(ans)
if ar != 0:
    ans.insert(-ar, "a")
```

である。

その後、

```python
print(ans[0].upper(), end="")
for i in range(1, len(ans)):
    print("R"+ans[i].upper(), end="")
```

として、文字の間に全部 `R` を挟んでいる。

この発想はかなり良い。

文字列を

```text
A R C R A R C ...
```

のように、A/Cの間に必ずRがある形に限定すると、

```text
ARC -> CRA
```

は、A/Cだけを抜き出した列上で

```text
AC -> CA
```

という隣接swapになる。

したがって `f(S)` は、

> **A/C列における「Aが左、Cが右」にあるペア数**

と考えられる。

あなたは

```text
A^q C^(25-r) A C^r
```

を作っている。

ここで

```text
q = X // 25
r = X % 25
```

なので、

- 最初の `q` 個のAは、それぞれ25個のCとペアになる → `25q`
    
- 後ろに挿入したAは、右側の `r` 個のCとペアになる → `r`
    

よって

```text
f(S) = 25q + r = X
```

となる。

**方針そのものは完全に正しい。**

---

## 1回目のWA

コードは、

```python
ans.insert(-ar, "a")
```

だった。

問題は `ar = 0`。

Pythonでは、

```python
-0 == 0
```

なので、

```python
list.insert(-0, x)
```

は末尾ではなく**先頭へのinsert**になる。

例えば

```text
X = 25
q = 1
r = 0
```

なら、本来

```text
A CCCCC...(25個)
```

で転倒数25にしたい。

ところが余分なAを先頭に挿入するため、

```text
A A CCCCC...(25個)
```

となり、転倒数は

```text
2 × 25 = 50
```

になる。

つまり1回目のWAは、考察ではなく完全に

> **`r=0` という剰余境界の実装ミス**

である。

---

## 2回目のWA

修正後は、

```python
if al != 0:
    ans.insert(-ar, "a")
```

となった。

しかし条件に使うべきなのは商 `al` ではなく剰余 `ar`。

例えば、

```text
X = 12
al = 0
ar = 12
```

では追加Aが必要なのに、

```python
if al != 0
```

が偽なのでAを挿入しない。

結果、Cしかなく `f(S)=0` になる。

さらに、

```text
X = 25
al = 1
ar = 0
```

では条件が真なので依然として

```python
insert(-0, "a")
```

が実行される。

したがって2回目は、1回目のバグの原因を

> 「`insert(-ar)` の `ar=0` が危険」

ではなく、

> 「Aを挿入する条件が何か」

というところで取り違えている。

最終的な

```python
if ar != 0:
```

で正しくなった。

# 3. C - Sum of Average 2

あなたの提出：

- [78984489 - RE](https://atcoder.jp/contests/arc229/submissions/78984489)
    

まずRE原因から。

## REの直接原因

最後が、

```python
for i in range(n):
    ans += (ansl[i] + ansl[i+1]) // 2
```

となっている。

`ansl` の長さは `n` なので、

```text
i = n-1
```

のとき

```python
ansl[n]
```

へアクセスしてRE。

正しくは、

```python
for i in range(n - 1):
```

である。

あるいはPythonなら、

```python
ans = sum((x + y) // 2 for x, y in zip(ansl, ansl[1:]))
```

とすると、今回の添字ミス自体が発生しない。

ただし、**ここだけ修正してもWAになる。**

---

# Cの本質

まず、

⌊x+y2⌋=x+y−[x≢y(mod2)]2\left\lfloor\frac{x+y}{2}\right\rfloor = \frac{x+y-[x\not\equiv y\pmod2]}2

と書ける。

つまり隣り合う2数について、

- 同じ偶奇 → `(x+y)/2`
    
- 異なる偶奇 → `(x+y-1)/2`
    

となり、**偶奇が異なる隣接には1/2のボーナスがある**。

ある並び

B1,B2,…,BNB_1,B_2,\dots,B_N

について全部足すと、

2F=2∑Ai−(B1+BN)−T2F = 2\sum A_i - (B_1+B_N) - T

となる。

ここで `T` は

> 隣接する2要素の偶奇が異なる箇所の個数

である。

`2 ΣA_i` は並べ替えても変化しない。

したがって最小化したいなら、

B1+BN+TB_1+B_N+T

を最大化すればいい。

ここで初めて、

1. **端点には大きい値を置きたい**
    
2. **内部では偶奇をできるだけ交互にしたい**
    

という2つの条件が同時に現れる。

---

# あなたの方針

あなたは、

```python
a = sorted(map(int,input().split()))
gk = [[], [], []]

for i in range(n-1):
    if a[i]%2==0:
        gk[1].append(a[i])
    else:
        gk[2].append(a[i])
```

として偶奇に分け、

```python
ansl = [a[-1]]
guuki = -1 if a[-1] % 2 == 0 else 1
```

最大値から開始。

その後、

```python
poped = gk[guuki].pop() if gk[guuki] else gk[-guuki].pop()
ansl.append(poped)
guuki *= -1
```

として、できるだけ偶奇を交互にしている。

## 良かった点

**偶奇が異なる隣接を増やすべきことには気付いている。**

これはCの重要な本質の一つ。

したがってCでも、完全に方向違いの考察をしていたわけではない。

---

# しかし「端点」の効果を落としている

例えば、

```text
A = [1, 3, 3]
```

を考える。

あなたのアルゴリズムでは、

```text
[3, 3, 1]
```

となる。

答えは、

```text
floor((3+3)/2) + floor((3+1)/2)
= 3 + 2
= 5
```

しかし、

```text
[3, 1, 3]
```

なら、

```text
floor((3+1)/2) + floor((1+3)/2)
= 2 + 2
= 4
```

でより良い。

原因は、

```python
ansl = [a[-1]]
```

と最大値を片端に置くところまでは良いものの、

> **もう片方の端点を管理していない**

こと。

内部の値は目的関数中で2回登場するが、端点は1回しか登場しない。

したがって大きい値を内部に置くより、

> **大きい値を両端に逃がす**

ことが重要になる。

あなたのコードは `pop()` で大きい値から内部へ入れてしまうため、最後に小さい値が端点へ残りやすい。

# Cubberの方針

[Cubber 78962336](https://atcoder.jp/contests/arc229/submissions/78962336)

かなりあなたの方針に近いが、一箇所決定的に違う。

```cpp
res[0] = a[n - 2];
res[n - 1] = a[n - 1];
```

最初に**最大2要素を両端として予約している**。

そのうえで残りについて、

```cpp
if (res[i - 1] % 2 == 1 and !even.empty()){
    res[i] = even.front();
    even.pop();
} else if (res[i - 1] % 2 == 0 and !odd.empty()){
    res[i] = odd.front();
    odd.pop();
}
```

と偶奇を交互にしている。

つまり、

```text
端点の価値
+
偶奇遷移の価値
```

の両方を扱っている。

あなたのコードとの差を一行で表すなら、

```text
あなた:
最大値を片端に置いて、残り全部を偶奇greedy

Cubber:
最大2値を両端に確保して、内部だけ偶奇greedy
```

である。

ここがCの最大の改善点。

# あなたの方針を活かしてCを書き直すなら

Cubber型をPythonにすると次のようになる。

```python
from collections import deque

def solve():
    n = int(input())
    a = sorted(map(int, input().split()))

    even = deque()
    odd = deque()

    for x in a[:-2]:
        if x % 2 == 0:
            even.append(x)
        else:
            odd.append(x)

    res = [0] * n
    res[0] = a[-2]
    res[-1] = a[-1]

    for i in range(1, n - 1):
        if res[i - 1] % 2 == 1 and even:
            res[i] = even.popleft()
        elif res[i - 1] % 2 == 0 and odd:
            res[i] = odd.popleft()
        elif even:
            res[i] = even.popleft()
        else:
            res[i] = odd.popleft()

    ans = sum(
        (res[i] + res[i + 1]) // 2
        for i in range(n - 1)
    )

    print(ans)


T = int(input())
for _ in range(T):
    solve()
```

これはあなたの

```text
偶奇を分ける
↓
交互に置く
```

という考えをほぼそのまま残している。

変更点は、

> **最大2要素を先に端点として抜く**

こと。

したがってCについては、考察を全部捨てる必要はなく、

```text
偶奇greedy
```

の前に

```text
なぜ偶奇greedyなのか？
目的関数を展開すると他に何が残るのか？
```

まで計算するだけでAC方針にかなり近づいていた。

# 7. 今回の弱点

## ① 「本質を1個見つけた時点」で実装へ進んでいる

A：

```text
転倒数
```

まで見えた。

C：

```text
偶奇遷移
```

まで見えた。

しかしCにはさらに

```text
端点
```

が残っていた。

一般化すると、

> 「ある特徴が重要だ」と分かった後、すぐgreedyを書くのではなく、**目的関数をその特徴だけで完全に表せるところまで変形する**

という一段が必要。

今回の上位勢との差として最も大きい。

---

## ② 境界条件確認が不足している

Aの2WAはどちらも、

```text
X mod 25
```

の境界だけで発見できる。

CのREは、

```text
長さnの配列の隣接ペア数はn-1
```

という確認だけで発見できる。

難しい反例ではない。

今回に限れば、新しい典型を大量に勉強するより、

> **完成した方針を1〜2分で壊しにいく習慣**

の方が即効性が高い。

# 8. 優先して直したいこと

## 優先度1：構成問題で「不変量」をコメントに書く

Aなら実装前に、

```python
# f(S) = number of (A before C) pairs
# X = 25*q + r
# construction gives 25*q + r pairs
```

まで書く。

こうすると、

```python
if al != 0
```

を書いた瞬間、

> 「追加Aの役割はr個分なのに、なぜqを条件にしている？」

と気付きやすい。

---

## 優先度2：貪欲の前に目的関数を展開する

Cなら、

```text
floor((x+y)/2)
```

を見た段階で、

(x+y−[odd])/2(x+y-[odd])/2

まで展開する。

すると、

```text
ΣA
端点
偶奇遷移数
```

しか残らない。

この形まで落としてからgreedyへ進む。

---

## 優先度3：提出前にコードの「個数」を確認する

今回なら、

```python
for i in range(n):
    ansl[i+1]
```

に対して、

```text
要素 n 個
隣接ペア n-1 個
```

と確認するだけ。

特に、

- `i+1`
    
- `i-1`
    
- `a[-1]`
    
- `insert`
    
- `pop`
    

を使った場所だけ提出前に見る、というチェックでも今回のRE/WAのかなりの部分を防げる。

# 総評

今回のARC229を見る限り、最も問題なのは「何も思いついていない」ことではない。

むしろ逆で、

- Aでは正しい直接構成を作れている
    
- Cでは正解方針の重要要素である偶奇に気付いている
    

ので、**着眼点はかなり正解寄り**だった。

しかし、

```text
着眼
→ 数式化
→ 証明
→ 実装
→ 境界確認
```

のうち、

```text
着眼
→ 実装
```

へ少し早く飛んでいる。

上位勢、特にCの sqrt23 / StarSilk は、

```text
順列問題
↓
端点と偶奇遷移数だけの問題
```

まで情報を圧縮してからコードを書いている。

CubberはAでもCでも、

> 正しさがコードの構造から分かりやすい実装

を選んでいる。

今回の比較対象から特に真似する価値があるのは、この2点だと思う。

### 今回の最重要課題

> **「正しそうな方針」を見つけた後、コードを書く前にもう1段だけ数式・不変量へ落とす。**

これができれば、Aの2WAも、Cの方針WA相当もかなり減らせる。

そして今回のデータだけを見るなら、難しいD/E/Fの勉強へ進むより先に、**AをCubber型と自分型の2通り、CをCubber型とsqrt23型の2通りで再実装する**のが最も直接的な復習になる。
